AES 41
Abstract
AES41 provides for the carriage of audio meta-data by embedding it in the audio samples
themselves. This tightly associates the meta-data with the audio, yet makes it fragile so that
changes to the audio will invalidate the meta-data. Several meta-data sets have been defined,
covering applications such as cascaded compression (bit rate reduction), and loudness control.
This Part specifies the method by which a meta-data set is embedded in the audio samples. Other
parts define the content and format of the meta-data sets.
PART 1
0 Introduction
0.1 Rationale for this standard
It has become apparent that there are requirements for the transport of audio meta-data together
with the related audio, in a way such that the two are not separated. Further, there are requirements
where any alteration of the audio should render the related meta-data invalid. Meta-data held in
files, or transported in associated video signals, or in AES3 user bits, for example, does not meet
these requirements: The meta-data may become dissociated from the audio, or may continue to be
associated with the audio even after substantial changes have been made.
Initially, this standard was developed to satisfy these requirements, of tight association and fragility,
for an application in cascaded digital compression (bit rate reduction).
Other applications have been identified that have these same two requirements, including the
carriage of meta-data to describe loudness.

7 Semantics of the bit-stream syntax [remove “coder control” wording]
The data_frame syntax shall be as described in this clause.
header

Part of the bit stream containing synchronization and content indicators.

data
Part of the bit stream containing information about the audio signal (for example,
previous encoding, loudness information).
error_check Part of the bit stream containing information for error detection.
ancillary_data Part of the bit stream that may be used for ancillary data.
7.1 Header
The first 54 bits constitute the header information which is common to all audio coder control data
types, where:
synchronization_word is the bit string ‘0000 0000 0000 0000 0000 0001 1111 1011’;
length is the number of bytes (octets) in the recoding_data_frame following the length count, up to
and including the last bit of the CRC, whereby padding_bits in the data ensure that the length is a
multiple of 8 bits;
type indicates the type of data that follow. See Table 1;
flags are bits indicating the validity of fields in the audio coder control data frame header;
introduced_time_offset_flag
is a 1-bit flag, which when set to logic 1 indicates that the
introduced time offset field in the header is valid; when set to logic 0 it indicates that the
introduced time offset field is not valid (in which case the introduced_time_offset should be set to
logic 0);
introduced_time_offset
indicates a time offset, measured in sample periods, by which
the audio signal has been shifted with respect to a reference time. A positive offset represents a
delay, a negative offset indicates that the audio signal is in advance of the reference time. The time
offset is represented by a signed integer with the most significant bit inverted to reduce the
probability of imitation of the synchronization word.

7.3 Syntax for error_check
Where:
crc_check
is a 16-bit cyclic redundancy check word used for optional error detection within the
audio coder control data stream.
This field is byte-aligned with respect to the start of the header. The bits included in the CRC check
are all those in the header and data sections. The generator polynomial for this check word is:
G(X) = X16 + X15 + X2 + 1
The method is depicted in Figure 1. The initial state of the shift register T should be ‘1111 1111
1111 1111’. All the bits to be included in the CRC are shifted into the shift register in the order in
which they occur in the audio coder control data bit stream. After the last shift operation, the
outputs b15...b0 constitute the CRC word to be used.

7.4 Syntax for ancillary_data
Where:
ancillary_bit
carries optional information conveyed according to a user-defined format
The number of ancillary bits equals the total number of bits that can be transmitted during one audio
frame minus the number of bits in the data_frame.
The minimum data_frame length is the length of the header plus the length of the
error_check. This would be the case when the meta-data type is set to logic 0 (undefined).

8 Method of signaling the meta-data bit stream on the AES3 interface
Three signaling methods are defined for use with the AES3 interface, according to the resolution
(bits/sample) of the systems that are to be interconnected. The methods signal the data bit stream by
altering the parity of the audio samples. Even parity indicates a data bit with value logic 0, odd
parity indicates a value of logic 1.
If an audio channel can only transport the sixteen most significant bits of the AES3 sample value,
then the data should be carried by having the sixteenth most significant bit set so that the parity of
the sixteen most significant bits is as required.
If the audio channel can transport twenty or more bits transparently, then the data should be
signaled by having the twentieth most significant bit set so that the parity of the twenty most
significant bits is as required.
If the audio channel can transport twenty four or more bits transparently, then the data should be
signaled by having the twenty-fourth most significant bit set so that the parity of the twenty-four
most significant bits is as required.
If a monophonic audio signal is being carried on one channel of an AES3 interface, the data should

be signaled in the same channel as the audio signal is being carried.
If an audio signal consisting of two channels (either stereophonic or independent) is being
transmitted on an AES3 interface, separate data should be signaled for the two channels. The data
for each channel should be sent in the channel in which the signal to which it relates is being
transmitted.
Channel status data shall indicate that the interface is being used for audio.

PART 2 MPEG-1 and MPEG-2 LSF Layer II meta-data
0 Introduction
AES41 provides for the carriage of audio meta-data by embedding it in the audio samples
themselves. This tightly associates the meta-data with the audio, yet makes it fragile so that
changes to the audio will invalidate the meta-data. Several meta-data sets have been defined,
covering applications such as cascaded compression (bit rate reduction), and loudness control.
This part describes the format for the data to be transmitted with audio decoded from MPEG-1
Layer II or MPEG-2 LSF Layer II encoding. The data may be used to aid a subsequent re-encoding
process. The presence of this data in the stream is indicated by type, as defined in Part 1 of this
standard, equal to 2.

0.1 Rationale for part 2 of this standard.
Digital compression techniques allow the use of lower bandwidth channels and less storage space
or, conversely, allow faster transmission and the storage of more program material. Digital
compression will be used for a significant amount of program acquisition, for program production
and storage, and for distribution and broadcasting.
Compression systems add impairments to sound. The audibility of these impairments depends on
the degree of compression and the techniques used.
It has been proved that re-encoding with minimal impairment can be achieved by using information
describing the previous encoding process. The information that is preserved varies according to the
encoding scheme that has been used, but might include framing and quantization resolution data.
