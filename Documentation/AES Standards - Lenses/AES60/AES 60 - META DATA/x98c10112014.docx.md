Abstract

This standard provides a vocabulary to be used in describing structural and administrative metadata about the processing and handling history of audio objects during audio preservation activities. Introduction

This standard sets out the vocabulary to be used in describing the processing and handling history of audio objects in audio preservation work. This metadata, sometimes referred to as ‘process history’, 'digital provenance' (or ‘digi-prov’), describes the details of how audio objects are treated and/or migrated. Essentially it provides the ‘who’, ‘where’, ‘what’, 'when' and ‘how’ information that clarifies the provenance of the audio object with regard to the work that has been done to restore and/or preserve the object. This vocabulary is expressed in the form of an Extensible Markup Language (XML) schema. By doing so it provides a structured human readable instance document that can be easily parsed and manipulated using any of a number of freely available programming libraries and tools.

1 Scope

This standard concerns the technical documentation of the processing and handling of audio files and physical audio formats carried out during audio preservation and restoration work. This documentation, here referred to as metadata, provides a description of where the work occurred, who did the work, when the work was completed, and how the work was done, including a full description of the audio signal chain as it was configured during the processing.

3 Definitions and abbreviations

3.1 Audio object

A general term used to describe physical audio carriers, and digital audio in the form of files and streams.

For the purposes of this document, the term physical audio carriers shall be understood to mean only those carriers to which an audio data essence is intrinsically bound to the physical object. For example, an audio DAT tape is a physical digital audio object. Wave files on the other hand are file based digital audio objects. They can be moved, copied, and renamed without the need to play the audio essence. In the latter case, the file exists on a storage device, but it is not intrinsically bound to that device. Therefore there is no need to describe the physical storage given its transient nature.

For additional details see AES57-2011, AES standard for audio metadata – Audio object structures for preservation and restoration.

3.2 Instance Document

A document that conforms to the minimally required set of elements and attributes defined by an XML schema.

3.3 Signal graph

An input through output tracing of all audio signal routing through a series of devices and or software describing the total processing applied to the audio signal during a process event.

Figure 1. Example of a Signal graph

3.3.1 Patching

Signal flow is expressed by forming relationships between channels of three types of  elements. They are device elements, module elements and media elements. A device element represents a single audio device in the signal graph. It may contain 01..n module elements, which each represent a sub-processor of the device. Media elements contain an audioObject element which has stream elements that represent audio channels from a media source orto a media destination. Patching is the process of forming ID-IDREF relationships between streams and channels of devices, between multiple devices, between devices and their modules, and between multiple modules within a device to describe the audio signal flow.

3.3.1.1 Device and module patching

Device channels and module channels are dievided into inputChannels and outputChannels for each type of element. Each of these channel elements in turn has an attribute that indicates an incoming signal and one that indicates an outgoing signal. This allows the signal graph to express both relationships between external devices as well as an internal signal path for each device through the use of module elements. In this scheme, a device’s input channels can be routed to the inputs of different modules or to the device output channels.

In all cases, these elements shall use ID-IDREF relationships to express the signal routing.

When forming relationships between devices or within a device and its modules the following rules shall apply:

Rule 1

A device outputChannel may be patched to one or more device inputChannels. In this configuration the outputChannel’s outgoingSignal attribute shall reference the ID attributes of all of the device inputChannels that it sends signal to. A reciproical link shall be formed by setting the destination device inputChannel’s incomingSignal attribute to reference the ID of the device outputChannel.

Rule 2

A device inputChannel may be patched to one or more module inputChannels. In this configuration the device inputChannel’s outgoingSignal attribute shall reference the ID attributes of all of the module inputChannels that it sends signal to. A reciproical link shall be formed by setting the module inputChannel’s incomingSignal attribute to reference the ID of the device inputChannel.

Rule 3

A module outputChannel may be patched to one or more module inputChannels provided that all modules reside in the same device. In this configuration the module outputChannel’s outgoingSignal attribute shall reference the ID attributes of all of the module inputChannels that it sends signal to. A reciproical link shall be formed by setting the module inputChannel’s incomingSignal attribute to reference the ID of the module outputChannel.

Rule 4

A module outputChannel may be patched to one or more device outputChannels In this configuration the module outputChannel’s outgoingSignal attribute shall reference the ID attributes of all of the device outputChannels that it sends signal to. A reciproical link shall be formed by setting the device outputChannel’s incomingSignal attribute to reference the ID of the module outputChannel.

Rule 5

A device inputChannel may be patched to one or more of the same devices outputChannel. In this configuration the device inputChannel’s outgoingSignal attribute shall reference the ID attributes of all of the device outputChannels that it sends signal to. A reciproical link shall be formed by setting the device outputChannel’s incomingSignal attribute to reference the ID of the device inputChannel.

These rules make it possible to represent a straight one- to -one connection or to represent a signal multiplier, but not a signal mixer.

3.3.1.2 Media patching

In addition to input and output channels, devices also may have media channels. Media channels represent the  ability of the device to play an audio signal from or record an audio signal to media that the device is equipped to play or record.

This standard defines media elements to represent the real world media object. Each media element contains an audioObject element which in turn contains one or more region elements. The regionRef attribute of the media element sets the scope of the media element to a particular region of the child audioObject element. This region element contains one or more stream elements, each with a unique ID attribute. The value of this ID attribute shall be used as the value of the incomingStream attribute on inputMediaChannels when the media was played during the process event. The value of this ID attribute shall be used as the value of the outgoingStream attribute on outputMediaChannels when the media was recorded during the process event.

When forming relationships between a device’s media channels and an audio stream the following rules shall apply.

Rule 6

When representing the playback of a media object, the value of the ID of the audioObject’s stream element shall be used as the value of the playbackMediaChannel elements incomingStream attribute. The outgoingSignal attribute of the playbackMediaChannel element may be patched to one or more of the device’s module inputChannel elements or to one or more of the same devices outputChannel elements. Accordingly, the value of the ID attribute of the patched module inputChannel or of the device outputChannel shall be used as the value of the outgoingSignal attribute.

Rule 7

When representing the recording of a media object, the value of the incomingSignal attribute of the recordMediaChannel shall be set to the value of the ID of either the last module outputChannel in the device signal graph or to the ID of a device inputChannel if the device contains no modules. The value of the recordMediaChannel elements outgoingStream attribute shall be set to the value of the ID attribute of the audioObject stream element that represents the recorded audio.

4.3.9.5 eventTimeline

The eventTimeline element shall be used whenever the processEvent contains work that involves media playback, media recording, or other media processing that involves reading or writing audio data in relation to an audio clock source. When present the eventTimeline shall provide a time-line comprised ofing a start time address and a duration measured from that starting point. This time-line is an abstract representation of presentation time which extends from the start time uninterrupted through to the end of the time-line as determined by the given duration.

NOTE Start time + duration equals the end point of the time-line.

All media elements and other time -based processing information (e.g. device parameters) shall be referenced to the eventTimeline element. The edit unit rate of the eventTimeline shall be set to the same edit unit rate of the media used in the processEvent. If the processEvent contains media of differing edit

unit rates, the media with the highest resolution edit unit rate shall determine the edit unit rate of the processEvent.

The eventTimeline element data type shall be aes57:timeRangeType as described in AES57-2011, AES standard for audio metadata – Audio object structures for preservation and restoration.
